# gRPC vs JSON 파일 업로드 비교

악성코드 다운로드 탐지 플랫폼([2026-Teecher-Team-C](https://github.com/2026-Teecher-Team-C))에서 로컬 에이전트가
검사 서버로 파일(최대 500MB)을 올리는 방식을 gRPC client-streaming으로 정했다. 이 레포는 그 선택을 측정으로
검증한 실험이다. 결정은 먼저 내렸고, 이 실험은 2026-10-16에 따로 했다.

## 비교한 것

| 방식 | 클라이언트 | 서버 |
|---|---|---|
| JSON | 파일을 base64로 인코딩해 `{"sha256","filename","data"}` 하나로 POST | 본문 전체를 읽고 파싱·디코딩한 뒤 디스크에 씀 |
| gRPC | 64KB 청크로 client-streaming | 청크를 받는 대로 디스크에 씀 |

두 방식 모두 Python(표준 `http.server` / `grpcio`)이라 언어 차이는 섞이지 않는다. 조건마다 서버 프로세스를
새로 띄우고, 최대 메모리는 각 프로세스의 `ru_maxrss`로 잰다.

## 결과 (macOS, Apple Silicon, 같은 장비 안 loopback, 조건별 2회)

| 파일 | 방식 | 전송량 | 시간 | 서버 최대 메모리 | 클라이언트 최대 메모리 |
|---|---|---|---|---|---|
| 50MB | JSON | 66.7MB | 0.65–0.69s | 261MB | 261MB |
| 50MB | gRPC | 50.0MB | 0.17–0.44s | 42–46MB | 36–41MB |
| 200MB | JSON | 266.7MB | 2.58–3.08s | 729–976MB | 976MB |
| 200MB | gRPC | 200.0MB | 0.48–0.72s | 43MB | 36MB |

원본 측정값은 [`results-2026-10-16-macos.jsonl`](results-2026-10-16-macos.jsonl).

- JSON은 base64 때문에 전송량이 약 33% 늘고, 원본·base64·JSON 문서·디코딩 결과가 동시에 메모리에 올라
  메모리가 파일 크기에 비례해 커진다(파일 크기의 약 4~5배).
- gRPC 스트리밍은 파일 크기와 상관없이 메모리가 약 40MB로 일정했다.

## 한계

- 비교 대상은 **단순한 JSON 업로드**다. REST라도 multipart·청크 업로드를 직접 구현하면 메모리 문제는 줄일
  수 있다. gRPC를 고른 이유는 그 스트리밍과 재조립이 기본 기능이라는 점이다.
- 같은 장비 안에서 주고받아 네트워크 지연은 거의 빠져 있다. 실제 네트워크에서는 JSON의 33% 추가 전송량이
  시간에 그대로 더해진다.
- 조건별 2회라 시간은 편차가 있다. 전송량과 메모리는 실행마다 거의 같았다.

## 다시 돌리기

[uv](https://docs.astral.sh/uv/)가 필요하다.

```bash
./run.sh                       # 50MB, 200MB 각 2회
SIZES="500" TRIALS=3 ./run.sh  # 크기·횟수 바꾸기
```

결과는 `results.jsonl`에 한 줄씩 쌓인다.
